De la règle à la mesure : la réponse active

En haut, la détection : un échec de connexion Windows devient une alerte 60204 quand il se répète. En bas, la réponse : le manager demande à l'agent qui a vu l'alerte de bloquer l'IP source dans le pare-feu Windows, puis de la débloquer 180 s plus tard.

  • Une règle, c'est un test sur des champs

    <rule id="100100" level="8">
  <if_sid>61603</if_sid>
  <field name="win.eventdata.image"
         type="pcre2">(?i)\\powershell\.exe$</field>
  <description>…</description>
  <mitre><id>T1059.001</id></mitre>
</rule>

    Une règle enfant (if_sid) ne s'évalue que si son parent a correspondu. On étend le ruleset natif sans le modifier, dans local_rules.xml, avec un ID de 100000 à 120000.

  • Une mesure, c'est deux blocs

    <command> déclare quoi exécuter (le nom du fichier dans active-response\bin). <active-response> dit quand (rules_id, level ou rules_group), où (local, server, defined-agent, all) et combien de temps (timeout).

  • Pourquoi pas la commande netsh native

    Le script natif cherche l'IP dans data.srcip. Sur nos alertes 60204, ce champ est vide : l'IP est dans data.win.eventdata.ipAddress (vérifié sur le manager). D'où block-ip-win.ps1, qui lit le bon champ.

Sources : documentation Wazuh 4.14, « Active response » et « Rules syntax » ; règles natives lues dans /var/ossec/ruleset/rules/0580-win-security_rules.xml du lab. Writeup 07.
