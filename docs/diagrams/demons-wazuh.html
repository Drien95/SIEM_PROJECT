SIEM_PROJECT · Wazuh 4.14 · qui fait quoi

Les démons de Wazuh, de l'agent au dashboard

ossec.conf dit quoi faire, les démons le font, l'indexer et le dashboard sont l'endroit où l'on regarde. Chaque boîte est un processus, chaque flèche un échange réel, avec les trois branches qui partent de l'analyse : intégrations (VirusTotal), réponse active, détection de vulnérabilités.

ossec.conf : le quoi

Un fichier déclaratif par machine. Sur le manager : <remote> (écoute 1514, syslog 514), <integration>, <command> et <active-response>, <vulnerability-detection>. Sur l'agent : <localfile>, <syscheck>, <sca>, souvent poussés depuis le manager par agent.conf.

wazuh-analysisd : le cerveau

Trois passes sur chaque événement : pré-décodage (horodatage, hôte, programme), décodage (les champs : srcip, win.eventdata.*, hash…), règles (ruleset natif puis local_rules.xml, niveau, corrélation frequency/timeframe). wazuh-analysisd -t charge tout et s'arrête : à lancer avant chaque redémarrage.

La boucle VirusTotal

Le FIM dit « ce fichier a bougé » et donne son hash. wazuh-integratord lit l'alerte, interroge VirusTotal, et sa réponse revient comme un nouvel événement dans analysisd : règle 87105 (niveau 12) si des moteurs détectent le fichier. Une réponse active peut alors le supprimer.

La réponse active fait l'aller-retour

analysisd décide, mais n'agit pas. Avec location local, l'ordre repart par wazuh-remoted vers l'agent, dont wazuh-execd lance le script : c'est ainsi que block-ip-win a bloqué Kali (writeup 07).

Sur Windows, les modules de l'agent (collecte, FIM, SCA, execd) tournent dans un seul service, WazuhSvc ; sur Linux, ce sont des démons séparés (wazuh-logcollector, wazuh-syscheckd, wazuh-modulesd, wazuh-agentd, wazuh-execd). Sources : documentation Wazuh, « Daemons » et « Architecture » (voir docs/architecture.md).
